## 3. 检索评测：口径、分母与结果

### 3.1 口径（必须先看）

- **K = 8**：应用实际返回的检索条数；所有命中率均指“前 8 条”。
- **可测用例**：该版本有预期文档，且预期行为为 `direct` 或 `partial`。`clarify`/`gap`/`tool` 不计入检索分母。
  - v1.2 可测：**22** 条；v1.3 可测：**71** 条。
- **文档命中（doc hit）**：
  - 宽松：任一预期文档进入前 8；
  - 严格：全部预期文档进入前 8。
- **引文命中（quote hit）**：
  - 对每条标准来源的 `quote` 做空白/表格竖线归一，检查是否出现在前 8 条证据文本中；
  - 严格：该用例的全部标准引文都出现；
  - 任一：至少一条出现；
  - 覆盖率：命中的引文数 / 全部标准引文数。
- **关键事实命中（key fact hit）**：
  - 检查 `required_facts` 的 `value`（金额、电话、日期等）是否出现在前 8 条证据文本中；
  - “任一”= 至少一个关键值出现；“全”= 全部关键值出现。
- **MRR**：第一个预期文档排名的倒数；没有命中记 0。

**三个不能混用的结论：**

1. **引文逐字匹配失败 ≠ 事实错误**。它只说明该段原文没有进入前 8，或引文写法与正文不完全一致；事实可能仍正确，只是证据没送到模型前。
2. **关键事实命中失败 ≠ 回答错误**。它说明具体数值不在检索上下文；回答层是否从别处得到、是否编造，需要生成层/人工判断。
3. **检索命中率 ≠ 回答正确率**。本轮没有跑生成/端到端，不能把 95% 的文档命中写成 95% 的回答正确率。

## 9. 如何对 API 版复测

当主线程把系统部署成 API（或提供远程地址）后，按以下步骤复测，不要直接套用本轮的本地检索结果：

1. **先记录版本**：`GET /health`、`GET /capabilities`、`GET /catalog`，记录 API 返回的应用版本、知识库版本、块数、模型名、是否离线。
2. **确认口径**：API 的检索条数 K 是否仍是 8；如果不是，先改 `retrieve_eval.py --k` 或在报告中写明新 K。API 的 `/ask` 是否返回 `sources`；如果字段不同，先适配 `e2e_eval.py` 的 `source_docs` 解析。
3. **跑端到端**：
   ```bash
   python -I scripts/e2e_eval.py \
     --cases cases/cases.jsonl \
     --base-url https://<api-host> \
     --run-dir runs/api-<date>
   ```
   记录原始请求/响应、耗时、超时、回退；凭据不要写进日志。
4. **跑生成层（如果 API 暴露模型或证据注入接口）**：
   ```bash
   python -I scripts/generation_eval.py \
     --cases cases/cases.jsonl \
     --endpoint https://<model-endpoint> \
     --run-dir runs/api-<date>
   ```
   如果 API 只暴露 `/ask`，不暴露模型，则只跑端到端；不要用本地 Qwen3 冒充 API 模型。
5. **分开报告**：API 版的检索命中率、回答正确率、工具通过率分别列分子/分母；不要和 v1.2 本地检索混算。
6. **人工复核**：至少覆盖所有 `critical` 用例、所有“外校/未公布/缺失资料”用例、所有工具计算。
7. **稳定性**：选 20 条核心用例，同一 API 版本重复 3 次，保留全部失败，不用重试掩盖首次失败。
8. **版本冻结**：如果 API 的知识库/模型与本轮不同，重新记录 SHA-256 或 API 版本号；本基线只对 v1.2/v1.3 两份索引和上述文件哈希负责。
